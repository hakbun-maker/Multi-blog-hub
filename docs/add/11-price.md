## 6. 개발 시 필수 준수 사항

> ⚠️ 기획·개발 팀이 반드시 숙지하고 구현에 반영해야 한다.

### 6-1. 플랜별 기능 권한은 단계를 철저히 끊어서 개발할 것

플랜 업그레이드 시 기능이 **단계적으로 정확하게** 열려야 한다.
예를 들어 Basic → Pro 업그레이드 시 키워드탐색기와 스케줄러는 열리지만,
**자동 글쓰기 · 자동 발행은 절대 열리면 안 된다.**
이를 뭉뚱그려 개발하면 나중에 권한 분리 수정에 큰 공수가 발생한다.

**구현 원칙**

- 모든 수익화 로켓 기능은 **기능 단위로 권한 플래그를 분리**하여 관리
- plan_id 기반으로 기능 ON/OFF를 결정하는 **중앙 권한 테이블을 별도 운영**
- 프론트엔드와 백엔드 **양쪽 모두** 권한 체크 로직 적용 (프론트만 막으면 API 직접 호출로 우회 가능)
- 잠긴 기능은 UI에서 **흐릿하게 노출 + 업그레이드 유도 CTA** 표시 (완전히 숨기지 않음)

**플랜별 기능 권한 테이블 설계 예시**


### 6-2. 할인 정책은 하드코딩 금지, 설정 테이블로 관리할 것

기본 연간 할인 외에 **이벤트·프로모션 추가 할인이 언제든 적용될 수 있다.**
할인율이나 금액을 코드에 직접 박으면 매번 배포가 필요해지므로 반드시 DB로 관리한다.

**할인 정책 테이블 필수 필드**

```
discount_policies 테이블
────────────────────────────────────────────────────────────────────────
id | type(rate/amount) | value | target_plan | target_billing(monthly/annual/all)
   | start_at | end_at | stackable(연간할인과 중복여부) | active | description
```

**지원해야 할 할인 유형**

- 정률 할인: 예) 20% 할인
- 정액 할인: 예) 10,000원 할인
- 적용 대상: 전체 플랜 / 특정 플랜 지정
- 적용 기간: 시작일 ~ 종료일 (없으면 상시)
- 중복 적용: 연간 기본 할인과 이벤트 할인 중복 여부 플래그
- 쿠폰 코드 방식 확장 가능하도록 구조 설계
